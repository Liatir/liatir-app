# Implementation Architecture

This page is internal project memory. It explains implementation
details that should not appear in the public user-facing documentation.

## App layers

Liatir is a Tauri 2 desktop application with a Rust backend and a SvelteKit
frontend.

| Layer | Technology |
|-------|------------|
| Desktop shell | Tauri 2 |
| Backend | Rust |
| Frontend | SvelteKit |
| Styling | Tailwind CSS v4 |
| Reactivity | Svelte 5 runes |
| Build | Vite |

## Frontend bridge

The frontend communicates with Rust through `window.Liatir`, typed publicly as
`LiatirBrowserAPI`. Direct `__TAURI__` calls should be avoided in app code; use
the local `liatir()` helper from `$lib/api.ts`.

```ts
import { liatir } from '$lib/api'
import type { LiatirBrowserAPI } from '@liatir/api'

const api = liatir() as LiatirBrowserAPI | null
if (!api) throw new Error('Liatir API not available')

const size = await api.invoke('lia_file_size', { path }) as number
```

If the local helper returns `any`, use `as` casts to narrow return types. Do not
rely on generic type parameters on `api.invoke<T>()` when the receiver is `any`.

## Rust backend

The backend is split into bridge modules under `src-tauri/src/bridge/`.

| Module | Responsibility |
|--------|----------------|
| `managed_bins.rs` | Filesystem ops, file preview, dependency checks |
| `job_runner.rs` | Process spawning, stdout/stderr streaming, job registry |
| `ipc_server.rs` | Axum server that proxies `lia_*` calls for Node.js plugins |
| `lia_runtime.rs` | `.lia` bundle validation, manifest parsing, execution |

Every `lia_*` command must be:

1. implemented as a `#[tauri::command]` function in a bridge module;
2. registered in `src-tauri/src/main.rs` in the `invoke_handler!` macro;
3. declared in `src-tauri/permissions/liatir-bridge.toml`.

Missing the permissions entry causes a "command not allowed" error at runtime
even if the command is registered in the invoke handler.

## Plugin IPC server

An Axum HTTP server starts on a random port when the app launches. Its address
and a Bearer token are written to `{app_data_dir}/.ipc`.

The IPC server is how `.lia` plugins call back into the Rust backend while they
execute. The Node adapter reads `.ipc` at plugin startup and authenticates with
the Bearer token. This lets plugin code call file, job, and result helpers
without exposing Tauri APIs directly.

## Tauri capability system

Tauri 2 has a strict capability model. Every command invokable from the frontend
must be listed in `src-tauri/permissions/liatir-bridge.toml` under
`[[permission.commands.allow]]`. The invoke handler registration alone is not
sufficient.

## Cargo template source of truth

`conf-templates/Cargo.template.toml` is the source of truth for
`src-tauri/Cargo.toml`. The actual `Cargo.toml` is generated by config scripts
that swap in dev, local, or production identifiers.

```bash
npm run localdevconf
```

Do not edit `src-tauri/Cargo.toml` directly unless the change is intentionally
generated or temporary.

## Frontend state management

Persistent stores live in `frontend/src/lib/stores/` and are built with Svelte 5
runes.

| Store | Contents |
|-------|----------|
| `dataFiles.svelte.ts` | Imported file registry |
| `analysisRuns.svelte.ts` | Run history persisted to app data |
| `jobs.svelte.ts` | Background job registry and UI state |
| `aiModels.svelte.ts` | AI Model registry and install/runtime status |

When adding runtime state, identify the real owner first: workspace, pipeline,
pipeline run, tool run, AI model job, plugin run, dependency install, or result
artifact. Do not introduce one global `running` state when multiple instances
can run or be saved independently.

## Native tool pattern

Native tool pages should follow the shared pattern:

1. check dependency availability;
2. render input form with format filtering;
3. start a job through the shared runner;
4. stream logs while running;
5. parse stdout/stderr into a shared output shape;
6. persist an analysis run;
7. render via the common result view.

This keeps UI, run history, Jobs, Results, and pipeline compatibility
consistent across tools.
